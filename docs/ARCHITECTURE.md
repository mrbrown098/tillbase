# Deployment architecture: one Tillbase, four ways to run it

Status: **proposal for owner approval. Nothing in this document is built, except model A.** Do not describe B, C or D as available in the README, release notes or the app until the acceptance criteria in section 9 are met and tested.

This document replaces nothing. [ONLINE-ACCESS.md](ONLINE-ACCESS.md) is an earlier sketch of one possible cloud design (client-side encrypted storage on a free hosting tier). Section 8 explains how it fits.

## 1. Goals and non-goals

Goals
- A shop chooses how it runs Tillbase, and can move between choices without losing data.
- One body of business logic, tested once, used by every deployment.
- No mandatory paid service, account or Tillbase-run server. No vendor lock-in: the customer can always export everything in open formats and walk away.
- No silent loss or overwriting of business records, in any model.

Non-goals (for now)
- A Tillbase-hosted cloud. A customer may host their own; the project does not have to.
- Real-time multi-writer collaboration across the internet.
- Replacing SQLite for local use. PostgreSQL is only for a central server a customer chooses to run.

## 2. What exists today (verified in the code, November 2026)

- `packages/core` (`@tillbase/core`): all business rules and the SQLite schema. It uses `better-sqlite3`, which is **synchronous**; services take a `Db` handle and run their work in transactions.
- `packages/desktop`: an Electron app. `electron/handlers.ts` is the only API the screens use (`TillbaseApi` in `shared/api.ts`) and is where **permissions are enforced** (`authorize(permission)`, 119 call sites). The renderer cannot reach the database.
- Money is integer minor units. Stock is the sum of an append-only `stock_movements` table. Customer balances come from an append-only ledger. Migrations are append-only, tracked with `PRAGMA user_version` (currently 9).
- Record IDs are generated by the application (`randomUUID()` for sales and ledger entries; each table's scheme must be confirmed in Phase 0). Receipt numbers come from one counter in the local database (`nextReceiptNo`), the terminal id defaults to `T1`.
- There is **no audit log table** and no server. Backups are SQLite file copies with a checked restore.

Two facts shape everything below: the logic is already separate from the screens (good), but it is synchronous SQLite code, and authentication and permissions live inside the Electron process (they must move to a place a server can share).

## 3. Principles

1. **One logic layer.** Rules live in `@tillbase/core` only. Servers and screens call it; they never reimplement it.
2. **One enforcement point.** Every permission check happens on the server side of the boundary (Electron main process today, the server process later) against the signed-in user's role, re-read on every call. A hidden button is never security.
3. **Clients never touch the database file.** Browsers and other computers talk to an API, never to SQLite or PostgreSQL directly.
4. **Money is integer minor units** end to end, in every database and every message.
5. **Append-only where it matters:** sales, payments, stock movements, ledgers. Corrections are new records (a void, an adjustment), never edits.
6. **Everything is versioned:** database schema, API, and sync messages. Old data upgrades; incompatible peers refuse to talk instead of guessing.
7. **Backups are only real if restored in a test.** Each deployment model ships with a restore drill.
8. **The customer owns the data:** full export in open formats (CSV and a documented JSON/SQL dump) from every model.

## 4. The four deployment models

### A. Standalone local/offline (exists)

Topology: the Electron app and one SQLite file on one computer. Security boundary: the computer itself plus the PIN login. No network needed. This stays the default and must never depend on B, C or D.

### B. Local network server

Topology: the owner's computer runs Tillbase and also serves a web interface on the shop's LAN. Tills, tablets and phones use a browser. One SQLite file, one writer (the server process). Clients never open the file.

Security boundary: the shop network. It is **not** safe to assume the LAN is trusted (guest Wi-Fi, a compromised phone, a neighbour on shared Wi-Fi).
- Off by default; the owner turns it on and sees the address and a pairing code.
- Each device is paired once (owner approves it); staff then sign in with their PIN. Wrong-PIN lockout applies per account and per device.
- TLS on the LAN: browsers treat plain HTTP as insecure and some features (camera, installable web app) require HTTPS. Options to decide: a per-shop local certificate authority the owner installs on devices, or plain HTTP limited to the LAN with the owner warned. This is an open decision (section 10).
- Bind to private addresses only; refuse requests that arrive via a public address or a proxy header the owner did not configure.
- Permissions: identical to today, enforced by the server for every request.

Dependencies: Phase 1 (service extraction) and the audit log.

### C. Customer-owned cloud

Topology: the customer (or their IT person) runs the same server on a machine they control (a VPS, a home server, a small container host) and reaches it through HTTPS. Tillbase provides the server software and instructions; it does not run or pay for anything.

Security boundary: the public internet. This is a different threat model from B and needs its own controls:
- HTTPS only, certificates from a public authority (for example through a reverse proxy such as Caddy). The server refuses plain HTTP.
- No direct exposure of a till's computer. Remote access to a *local* server (model B) goes through a customer-chosen secure tunnel or VPN, never an opened router port.
- Stronger authentication than a 4-digit PIN for remote sessions: owner/manager accounts use a long password and optional second factor; cashier PINs work only from paired devices. Rate limiting, lockout, and session expiry are required.
- Secrets (database credentials, session keys) are configuration, never committed, never in the client.
- Database: SQLite is acceptable for a small single-server shop; PostgreSQL is offered for central deployments (section 6). A single shop may start on SQLite and migrate to PostgreSQL with a tested tool.
- Client-side end-to-end encryption (as sketched in ONLINE-ACCESS.md) is incompatible with server-side reports and permission checks unless the server holds the keys. For customer-owned servers the customer *is* the data holder, so the simpler design (server holds the data, TLS in transit, encrypted disk and backups) is proposed. E2E remains an option only for a future third-party relay.

### D. Hybrid synchronisation (future)

Topology: each location keeps a full local database and keeps selling offline; a customer-owned central server collects and redistributes changes. Sections 7 and 9 describe the model. This is the highest-risk model and is built last.

## 5. The three kinds of access must not be confused

| | Local LAN (B) | Public remote (C) | Offline device sync (D) |
|---|---|---|---|
| Who is online | Device and server on the same network | Browser anywhere, server on the internet | Devices work alone, sync when they can |
| Data lives | Server only | Server only | On every device and the server |
| Main threat | Other devices on the LAN | Anyone on the internet | Divergent copies, lost or replayed changes |
| Required controls | Pairing, PIN lockout, private-address binding | HTTPS, strong auth, rate limiting, patching | Idempotent changes, conflict rules, reconciliation |
| Works with no internet | Yes | No | Yes |

A local server is **never** exposed to the internet directly. If an owner wants remote access to a local server, the design must route through a customer-controlled secure channel; until that exists in the product, the supported remote option is model C.

## 6. Shared building blocks

### 6.1 Server layer
Extract the transport-neutral part of `handlers.ts` (the `TillbaseApi` implementation and its permission checks) into a package that has no Electron imports. Electron's IPC and a future HTTP server are two thin adapters over it. Acceptance: the existing handler tests pass unchanged against both adapters.

### 6.2 Authentication and sessions
Today the signed-in user lives in the Electron process. The server layer needs real sessions: random session tokens, expiry, revocation, per-device pairing, and re-reading the user's role on every request so a demoted or deactivated user loses access immediately (the desktop handlers already do this).

### 6.3 Database abstraction
The services currently call `better-sqlite3` synchronously. PostgreSQL drivers are asynchronous, so "support both" is a rewrite of the data layer, not a setting. Proposed approach, in order of preference:
1. **Keep SQLite as the only database until a customer actually needs PostgreSQL.** A single SQLite writer comfortably serves one shop's tills on a LAN or one server.
2. When PostgreSQL is justified, introduce a small repository interface per aggregate (sales, stock, customers…) with two implementations, and make services async. Do it aggregate by aggregate, not in one change.
3. Keep one **schema definition per dialect** with a parity test that runs the same behavioural test suite against both. Known differences to handle: `PRAGMA user_version` vs a migrations table, SQLite's dynamic typing vs strict types, `INTEGER` money (use `BIGINT`), date functions, `COLLATE NOCASE`, upsert syntax, and transaction isolation.
Acceptance for PostgreSQL support: the full core test suite passes on both, an upgrade test migrates a real SQLite file into PostgreSQL and totals match to the minor unit.

### 6.4 Migrations and compatibility
Migrations stay append-only. Add a schema version handshake: a client or peer reports its schema and API version; the server accepts only versions it supports and says what to upgrade. A server never downgrades a database; a restore of an older backup upgrades it (already true for the desktop app). Every release is tested by upgrading a database created by the previous release.

### 6.5 Audit history and approvals
Add an append-only `audit_log` (who, which device, when, what action, which record, before/after for sensitive fields, reason text). Required for: voids, refunds, price and discount overrides, stock adjustments and write-offs, credit limit changes and write-offs, staff and permission changes, backup restore, settings changes, and sign-in failures. Optionally hash-chain entries so tampering is detectable. Configurable approvals (for example, a void above a limit needs a manager) are rules evaluated by the server layer, recorded in the audit log, and default to today's behaviour.

### 6.6 Backup, restore and portability
SQLite: keep the existing checked-copy backups (use the SQLite online-backup API when a server holds the file open). PostgreSQL: `pg_dump` plus a restore test. Every deployment documents and CI-tests a restore drill. A documented full export (CSV set plus a JSON or SQL dump with the schema) makes the data portable to another system.

## 7. Synchronisation model (model D)

Principle: synchronise **operations**, not whole databases, and make them safe to repeat.

- **Identity.** Every business record and every operation gets a globally unique ID generated on the device that creates it (UUIDv7 or equivalent). Every device has a permanent device ID and a per-device sequence number.
- **Operation log.** Each change is written, in the same transaction as the business change, to a local outbox: `{opId, deviceId, seq, entity, kind, payload, createdAt, schemaVersion}`. The server stores operations it has accepted and returns the ones the device has not seen.
- **Idempotent processing.** Applying the same `opId` twice has no effect. Gaps in `seq` are detected and re-requested.
- **Conflict rules by record type** (decided up front, never "last write wins" for money):
  - *Append-only records* (sales, payments, stock movements, ledger entries, audit entries): merge by union; no conflicts. Stock on hand is derived, so two tills selling the same item both reduce it correctly. Negative stock is allowed and flagged for review.
  - *Corrections* (void, refund) are new operations that reference the original. A void of a sale the server has not yet seen waits until the sale arrives.
  - *Editable master data* (product, price, customer details, settings): each record carries a version; concurrent edits create a **conflict item** shown to the owner with both versions. Nothing is dropped; the loser is kept in history.
  - *Numbers* (receipt numbers, order tokens): per-device prefixes or ranges so two devices never issue the same number.
  - *Limits* (customer credit limits, loyalty and wallet balances, gift balances): two offline devices can both spend the same allowance. This is accepted and reported, not hidden: the reconciliation screen lists customers who exceeded a limit because of concurrent offline sales.
- **Clock skew.** Order operations by a hybrid logical clock, never by the device's wall clock alone; flag devices whose clock is far off.
- **Reconciliation and recovery tools.** A report that compares counts and money totals per device and day between a device and the server; a "resend from sequence N" action; a rebuild of a device from a server snapshot after loss or corruption; a dry-run mode that shows what a sync would change before it runs.
- **No silent overwrite.** Any rule that would discard information instead creates a conflict item or an audit entry.

## 8. Relationship to the earlier online-access sketch

`ONLINE-ACCESS.md` proposed a client-encrypted store on a free hosting tier. Under this specification that becomes an optional **relay** for people who do not want to run a server: it only moves encrypted operations (model D) and cannot run reports or permissions, so it cannot replace models B or C. It is deferred and the sketch should be marked as such when this document is approved.

## 9. Phases and acceptance criteria

Each phase ships on its own, is optional for the shop, and leaves model A untouched.

**Phase 0: foundations (no new deployment mode)**
- Confirm and, where needed, migrate all record IDs to globally unique IDs (new migration, upgrade test on real previous-release data).
- Add `audit_log` and write to it from the sensitive actions in 6.5.
- Version the API and database handshake.
- Acceptance: every sensitive action appears in the audit log in tests; previous-release databases upgrade with identical sales, stock and ledger totals; no behaviour change for existing users.

**Phase 1: server layer extraction**
- Move the API implementation and permission checks out of Electron-specific code (6.1) and add real sessions (6.2).
- Acceptance: the whole existing desktop handler test suite passes through both the IPC adapter and a new HTTP adapter; a permission matrix test proves each role is allowed or refused identically on both.

**Phase 2: model B (LAN) on SQLite**
- Headless server mode, device pairing, a browser interface for the screens that make sense on a phone or tablet first (checkout, orders, kitchen), read-only reports.
- Acceptance: a second device completes a sale while the owner's till is also selling, with no lost or duplicated sales; a device that was never paired is refused; the server is unreachable from a public address in a documented test; stale sessions are rejected; a restore drill passes.

**Phase 3: model C (customer-owned cloud)**
- A documented container or package, HTTPS via a reverse proxy, strong authentication for remote sessions, rate limiting, update procedure.
- Acceptance: external security review of authentication, session handling and the public surface; automated scan clean; backup and restore drill on the hosted layout; clear documentation of what the customer must secure.

**Phase 4: PostgreSQL (only if needed)** per 6.3.

**Phase 5: model D (sync)**
- Outbox and operation log, idempotent apply, conflict items, reconciliation tools, simulated-chaos tests (duplicate, reordered, delayed and dropped messages; clock skew; two devices selling the same stock).
- Acceptance: property-based tests show that, after any delivery order, all replicas converge to the same totals; no operation is lost or applied twice; a conflict is never resolved silently.

## 10. Decisions needed from the owner

1. Approve this phasing, or change the order (for example, is model B or model C more valuable first?).
2. LAN TLS: local certificate authority per shop, or plain HTTP on the LAN with an explicit warning.
3. Whether PostgreSQL is wanted at all in the first versions (recommended: no, until a customer needs it).
4. Whether the project will ever offer a hosted option, or only self-hosting (this spec assumes self-hosting only).
5. Whether to mark `ONLINE-ACCESS.md` as superseded (recommended).

## 11. Risks

- **Rewriting services to async** for PostgreSQL is large and touches every service; mitigated by doing it only on demand and per aggregate.
- **Security surface grows sharply** with a server. Model C needs an outside review before it is called supported.
- **Sync correctness** is the hardest part of the project; it is last on purpose, and must not ship without the chaos and convergence tests.
- **Schema drift** between SQLite and PostgreSQL if parity tests are skipped.
- **Support burden** for self-hosters; mitigated by clear documentation and by making models B and C optional.
